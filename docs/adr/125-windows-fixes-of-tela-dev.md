# ADR-125: Windows fixes of `tela dev`

- **Date:** 2026-10-22
- **Status:** Accepted

## Decision

Windows fixes of `tela dev` (v0.9.1, from the first native run on a Windows 11 VM; amends ADR-112 and ADR-115). **Segments at Close** (ADR-112): `Backend.Close` released every window's segment right after flushing, so a Present that created a segment just before the end (the conformance suite's ConfigureThenFrame presents, then quits) reached a host that could no longer open it on Windows, where a named file mapping disappears with its last handle ("OpenFileMapping …: The system cannot find the file specified"). Close now waits, within the same second as the flush, until the host has acknowledged the latest segment of every window, open or closed, as a closed window already did; a lost connection ends the wait. A child that dies without Close can still leave the host one failed open, which stays a non-fatal host error (`-v` only in `tela dev`). The event-encoding test skips its comparison with package `platform`'s sources when the test binary runs outside the source tree (the round trips still run). **Removed names on Windows** (ADR-115): `ReadDirectoryChangesW`'s records do not say whether a removed or renamed-away name was a directory, and the watcher reported every extensionless name as a possible one, which a filter must accept: vim's `4913` probe passed a filter that accepts directories, and any extensionless file removed in the module (`LICENSE`, `Makefile`) rebuilt the app. Each root now keeps the set of its tree's directories (lowercased; walked while the first read is pending, so a directory created meanwhile is walked or reported, and again after an overflow; updated by the records), and only names in it are reported as directories. **A killed child** on Windows exits with status 1 (`Process.Kill` is `TerminateProcess(1)`; there is no signal), which the problem line reports as such; a test now expects the OS's wording. **Defender:** Microsoft Defender scans every new executable on its first run, and every reload is a new build: about 690 ms for a 29 MB build (12 ms on its second run); a reload of `examples/dashboard` took 2.2 s, and 1.1 s with the temporary directory and the Go build cache excluded (build 1.4 → 0.8 s, start → first frame 0.7 → 0.18 s). `tela dev` cannot avoid the scan and never changes the system's settings. On Windows, when a build takes more than 400 ms from its start to its first frame (90–180 ms without the scan), it prints once per session the likely cause, the directories to exclude from real-time scanning and the PowerShell command to run as administrator (`Add-MpPreference -ExclusionPath '…', '…'`); the note is also in `tela dev --help` and the CLI wiki page. So that a few directories cover every session and all of a build's files, Windows builds live in `%TEMP%\tela-dev\session-*` (the hint names `%TEMP%\tela-dev`; elsewhere sessions stay `tela-dev-*` in the temporary directory, since a fixed directory in a shared `/tmp` would belong to its first user) and the go command's temporary files (its `WORK` directory, where it compiles and links before copying the executable out) go to the session's directory through `GOTMPDIR`, unless the user set `GOTMPDIR`, which the hint then names too; `GOCACHE` and `GOTMPDIR` come from the `go env -json` that `tela dev` already runs (ADR-123). The threshold and the exclusions are supervisor settings, so the fake-child tests check the hint on every OS

## Rationale

Releasing a segment before the host acknowledged it was already wrong for a closed window (ADR-112 kept it); Close is the same case. Knowing the tree's directories is what inotify gets from `IN_ISDIR`, and a guess from the name cannot tell `4913` from a package directory. A scan the user did not ask for cannot be skipped by `tela dev`, and changing antivirus settings is the user's decision, so it explains once what the slow start is and how to avoid it, with one directory that covers every session instead of a new random one each time
