# ADR-117: The error overlay of `tela dev`

- **Date:** 2026-10-22
- **Status:** Accepted

## Decision

The error overlay of `tela dev` (phase 9, T5; implements G5 of ADR-111 on the overlay hook of ADR-112 and the `problemView` seam of ADR-115; amends §17). **View.** An `overlayView` in `cmd/tela`, composed with the terminal view (which keeps printing), draws the current problem (build, panic, exit, start; title, one-line summary, full text) as a panel built with Tela itself: `h` elements and Tailwind classes in a headless `core.Tree` (the embedded fonts, so it is deterministic; the supervisor's own process is a tool, so importing `tela`, `h` and `internal/core` from `cmd/tela` is allowed), rendered by Tela's rasterizer onto an image of the window's physical size and composited over the frame the host presents (`Host.SetOverlay`). A Tela tree always paints its canvas opaque first, so the tree is rendered twice, over black and over white, and each pixel's alpha and premultiplied color recovered from the difference (about 30 ms at scale 1, 100 ms at scale 2 for both renders, only when a problem appears or the window's size or scale changes; compositing costs a few ms per present). The panel is a dark zinc panel with a red (build, panic) or amber (exit, start) accent line, the title, the summary, a monospace body and a footer hint (`Save a change to rebuild · r reload (in the terminal) · Esc dismiss`); `r` is a terminal key only, since a window key would be typed into the app's fields while a docked panel leaves the app usable. In compiler output the `file:line:col` prefixes are emphasized and the `# package` headers dimmed; in a panic the value is red, the goroutine header dim, and the frames of the runtime, the standard library plumbing and Tela itself dim, so the app's own frames and their `file:line` stand out. Lines are never wrapped (one fixed-height line each, cut with an ellipsis), the body is clipped to the panel with a `… N more lines` note, and there is no scrolling. **Placement.** Decided by whether a child is alive and shown when the problem appears (`problem.live`, set by the supervisor): with one (a build error, or a new build that panicked, exited or timed out while the old one stays) the panel is docked at the bottom, up to 40% of the window (at least 220 logical pixels, less when the text is shorter) with a shadow, and the app above it stays visible and interactive; without one (the app panicked or exited, or nothing has started yet) the panel is centered over the last frame, dimmed by a 60% black scrim, up to 960 logical pixels wide and as tall as its text needs. The geometry (panel, close button, lines that fit) is computed in logical pixels before the tree is built, so input needs no layout pass. **Threads.** `show` and `clear` run on the supervisor's goroutine and only `Host.Post` to the UI thread, where all the view's state lives without locks and the draw function (called by the host while composing) renders on demand for the window's current size and scale, so a resize redraws without any event. While no problem is shown, or after it was dismissed, no overlay is set on the host: no composition, no cost. **Input.** New `HostOptions.Input func(w platform.Window, e platform.Event) bool`, called on the UI thread for every input event of a real window before it is queued (frozen) or delivered; true consumes it and no child sees it. A pointer that moves onto consumed ground gets a synthesized `PointerLeave` (at the last position the child saw), a `PointerEnter` is synthesized before the first event that is not consumed again, and the window's own `PointerLeave` arriving over consumed ground is dropped as the child already has one, so hover states cannot stick under a panel. A consumed key press needs no matching release consumed: the host's per-child keyboard view drops releases and repeats of presses the child never saw. The overlay consumes the pointer sequence that starts inside the panel (press, moves, release, even if the pointer leaves it), moves and scrolls over it when no button is held, and an Escape press; a press that starts in the app stays the app's even when dragged over the panel. A click on the `×` button (a press and a release on it) or Escape hides the panel until the next problem; the problem stays printed on the terminal; the next good build (promotion) clears it. `remote` still imports only `platform`, the standard library and `x/sys`. **Tests.** Goldens of a build error (docked, and over the first start), a panic with its stack, an exit and a start failure, at scales 1 and 2 over a fixed fake frame; supervisor tests with fake children on the headless backend compare the real window's presented pixels, exactly, with the overlay's own rendering over the child's frame (docked build error with the app clickable above the panel and not through it, Escape and the `×` dismissing, the next build clearing, a panic covering the window, resize and scale changes redrawing); `remote` tests for the `Input` option (consumption, hover bridging, window leave, keys, frozen input)

## Rationale

The window must say what is wrong where the developer is looking, without a second window or a closed one; drawing the panel with Tela keeps it crisp at any scale and in the framework's own style at no new dependency, and an overlay is the same mechanism the debug overlays use (ADR-062: pixels drawn over a private copy, nothing taking part in the app's layers). Docking only when an app is alive keeps a failed build from taking the working app away, while a dead app has nothing to keep usable. Rendering twice over opposite canvases is exact and needs no change to `core`, where the opaque canvas is a tree-wide invariant; a hook in the host's input path is the one place where events can be taken before the freeze queue and the child's keyboard view, which a handler in the supervisor could not do without reimplementing them
