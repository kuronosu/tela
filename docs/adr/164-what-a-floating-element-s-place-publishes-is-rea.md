# ADR-164: What a floating element's Place publishes is read in the same frame, and a menu clears

- **Date:** 2026-10-25
- **Status:** Accepted

## Decision

What a floating element's Place publishes is read in the same frame, and a menu clears its highlight when the mouse leaves an item (patch v0.10.2; engine, `aria`, no public API change; amends ADR-096, ADR-099, ADR-133 and ADR-141). **1. The flip's side styled a frame late.** A menu, popover, tooltip or select that flips (a context menu opened near the bottom of the window) was placed above its trigger in its first frame, as ADR-096 promises, but its classes came from `Placement`/`Side` published by `Place` and read by a build, which ran in the next frame (`publishAfterFrame`). Its first two frames were styled for the initial side (`bottom`: `origin-top`, `starting:-translate-y-2`), it entered sliding down from 8 px above, and at the third frame the rebuild changed the transform origin and the slide at once: a visible jump (measured: the menu's top at 63, 63, then 72 with the final at 71). The rebuild alone is not enough, because the box had already started its transition from the wrong starting style. **Rule:** a frame whose float pass published a Value that builds, layout or text read applies it before anything is shown. `Tree.Frame` runs its phases in a loop: after `paintPhase`, `rebuildPublished` takes the Values that `Place` published in the frame (`callPlace` records them) off the after-frame queue and invalidates their non-paint readers now; if any reader was hit, the frame builds, styles, lays out and paints once more (at most once per frame: what the second float pass publishes waits for the next frame as before). In that second pass a box that was styled for the first time in this frame (`Box.styledFrame == Tree.frame`) is restyled as new: its animation state is dropped and it transitions again from its `starting:` style, now with the classes of the final side. The first pass is never presented. Only Values published by a `Place` function take part (arrow offsets and `hide` data are paint-phase readers, already in the same frame), and nothing else changes for a popover that does not flip (the published placement equals the initial one: no reader, no second pass). Menus, popovers, tooltips and selects all go through `UsePopover`/`UseFloating`, so one change covers them; `Floating.Placement` is now "the engine's in the frame that shows the element" instead of "one frame behind" (documented in `aria/floating.go`, `aria/popover.go`, `internal/core/floating.go`). **2. The highlight stayed after the mouse left.** Compared with `@radix-ui/react-menu`: `MenuItem` calls `onItemLeave` on `pointerleave` of an item and on `pointermove` over a disabled one, and `MenuContent`'s `onItemLeave` focuses the content and clears the current item, so a menu with the mouse outside, or in a gap or on a separator, shows no highlighted item while keys still work (ArrowDown first item, ArrowUp last, typeahead). Tela had `OnPointerMove` focusing the item and nothing on leave, so the last item stayed highlighted. **Rule** (`aria/collection.go`, `onItemLeave`, menus only: `UseMenu`, so `DropdownMenu`, `ContextMenu` and `Menubar` menus; the listbox of `Select` keeps its own rule): a mouse (not touch) leaving an item, or moving over a disabled one, clears the focused key and gives the focus to the menu container (the state of a menu opened by the pointer), without the container's focus handler moving to the first item. Already as Radix: a menu opened by pointer has no item highlighted, one opened by the keyboard (Shift+F10, ContextMenu key, Enter, Space, ArrowDown on the trigger) has the first (ArrowUp the last); checkbox and radio items are items like the rest. **Tests (written, for the main session to run):** `aria/menu_test.go` (`TestMenuMouseLeavingAnItemClearsTheHighlight`, `TestMenuReopensWithTheRightItem`, `TestMenuCheckboxAndRadioItemsHighlightLikeOthers`), `kit/menuside_test.go` (a context menu, a dropdown menu and a popover that flip above: every frame from the first is at or below the final place and only moves up), `internal/core/floating_test.go` (`TestFloatingPublish` now expects the reader of the side to build in the first frame and the tree to be clean after it). **Goldens:** none changes (a golden is a settled frame). **Patch v0.10.3 (review fix): only the mouse's movement clears the highlight.** After scrolled content moves under a resting pointer, `rehover` (ADR-057) hit-tests it again and fires leave and enter events; in a long menu scrolled by ArrowDown under a resting mouse, the leave of the item that scrolled away cleared the highlight and the next ArrowDown went to the first item. Radix's scrolling fires no pointer events. **Rule:** the enter and leave events that `rehover` fires are marked (`core.Rehovered(e)`, internal, an unexported field of `PointerEvent`), and `onItemLeave` ignores them: the highlight stays on the item the keys reached until the mouse itself moves (a move over another item highlights it; a move out of the menu clears it). Test: `TestMenuKeysScrollUnderARestingMouse`. **Patch v0.10.3 (review fixes): the second pass restyles like any restyle, and every Place publish counts.** (a) "Restyled as new" applied to all of `restyle`: with no old style it skipped what a restyle does after the animations, so a flipped popover whose side classes changed an inherited value kept its children in the first side's color and font size, a display change kept the first structure (a block's paragraph instead of flex items), a text field inside kept its text style, and a `TextColorFn` on the box was counted again (never uncounted), so `textPaints` ran on every later paint; none of this healed in later frames. **Rule:** only the animations start again (the before-change style is nil: the entry runs from the final side's `starting:` style); the structure, the children's inherited values, a field's text and the `TextColorFn` count compare with the style the box had in the first pass. (b) The second pass is a new structure pass: `Frame` advances `Tree.frame` before it, as `virtualRelayout` does, so the per-frame marks (`boxFrame`, `inlineFrame`, `sibFrame`) do not skip what the first pass built; "styled for the first time in this frame" is `Box.styledFrame >= Tree.frameStart` (the counter at the start of `Frame`), which also restarts the entry of a popover with a `VirtualList` inside (its relayout had advanced the counter, and it entered from the first side's starting style). (c) `callPlace` took the entries a Place call appended to `Tree.pubs`, missing a Value already queued in the frame (a layout effect's `PublishValue`), whose readers then followed a frame late. **Rule:** `PublishValue` records every Value it publishes while a Place function runs (`floatTree.placing`, `placePublished`), also one already queued and also an equal value still pending from earlier in the frame. With ADR-162's build rule: a build's `PublishValue` is a direct store that queues nothing, so a later Place publish queues and is applied as any other; layout effects and other code in the frame still wait for the end of the frame unless a Place function publishes the same Value after them. Tests: `internal/core/floating_test.go` (`TestFloatingRerunRestylesWhatTheSideChanges`, `TestFloatingRerunCountsTextColorFns`, `TestFloatingRerunWithVirtualList`, `TestFloatingPublishAfterEarlierPublish`). No golden changes.

## Rationale

ADR-096's "no frame shows an element in the wrong place" stopped at the position: the side-dependent classes of every kit overlay are Go conditions on the placement, so the promise has to include them, as Radix's `data-side` is set before it starts the animation (`isPositioned`). Running the frame again where the Value was published keeps one rule for builds, no per-component "positioned" flag and no public API; the cost is one extra build, style, layout and paint in the frames where a popover flips, not in the frames where it does not. The highlight is Radix's behavior and what a native menu does: a pointer that has left the menu should not leave a row looking selected
