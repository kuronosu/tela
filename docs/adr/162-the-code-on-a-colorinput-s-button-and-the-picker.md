# ADR-162: The code on a `ColorInput`'s button and the picker's hex field follow a drag, and the

- **Date:** 2026-10-25
- **Status:** Accepted

## Decision

The code on a `ColorInput`'s button and the picker's hex field follow a drag, and the code keeps its width (patch v0.10.2; `kit`, and `aria.UseColorField` internally, no API change; amends ADR-143, which listed the text of the button among what cannot follow a drag without a build). **Live code:** the code is `h.TextFn(func() string { return aria.FormatHexColor(st.LiveColor(), alpha) })` in the small `colorInputLabel` component, the mechanism the swatch has (`BgFn(st.LiveColor)`): a move of the area or a slider changes the color's version value, the paragraph holding the text is laid out again and nothing builds (measured: 8 moves of a drag, 0 builds, the code changed on each; with and without `Alpha`). **Accessible name:** the button's `aria-label` (`label + ", " + code`, only when the button has a label; without one the name is its content, which is live) is a string of the last build, so it has the color the drag ended on when the drag ends (the drag's end builds) and mid-drag it shows the color of the last build, which catches up when the pointer rests 120 ms. **The hex field follows too** (the owner's follow-up: the field of an uncontrolled picker lagged the drag, since `aria.UseColorField` gave it `h.Value(code of the last build)`, and a controlled one only looked live because every move built). `UseColorField` now keeps the text in a `tela.Value[string]` and binds the input to it with `h.BindValue` (an existing prop: the field follows `v.Set` from anywhere and writes its edits to `v`; no new API, no `ValueFn`). `ColorState` keeps the fields that watch it (`watch`/`unwatch`, registered by an effect of the hook) and its `repaint`, which every move already calls, tells them (`follow`): each publishes the code of the color shown now with `core.PublishValue` (the UI thread's direct store, so the bound field changes before the frame and nothing builds), **unless the user is editing** (`editing`, set by the first accepted change of the text and cleared by a commit or an arrow key): then the draft stays, as in React Aria's `useColorFieldState`, and the next build (which also publishes `draft` or the code of the build, for a changed `Alpha` or a color the caller changed) and every commit put the code back. Enter and blur still commit (a code sets the color and the field shows its normalized form at once, `#f80` becomes `#ff8800`; anything else reverts to the code); a refused controlled change shows the old code after the build that follows; a paste that is not a prefix of a code is put back by publishing what the field showed; the caret goes to the end only when the text changes, as for any bound value. A press on the area or a slider blurs the field first, so a pointer drag cannot overlap an edit; the guard matters for keys, a controlled value changed from outside and a second pointer. Measured with a throwaway driver (builds and layouts of one pointer move): uncontrolled `ColorPicker` 0 builds and 0 layouts, the panel of a `ColorInput` 0 builds and 1 layout (the button's code), a controlled picker 2 builds and 1 layout, the same as before the change; the field showed the color after every move in the three. `TestColorHexFieldFollowsTheDrag` and `TestColorHexFieldKeepsTheDraft` assert it. **Fixed width:** Inter is proportional, so the button changed width with the digits (`#111111` is 63.3 px at `text-sm` and `#ffffff` 37.2 px). The code keeps `tabular-nums` (the digits are 9.078 px, `#` 8.866 px, and the lowercase letters a to f, which `aria.FormatHexColor` writes, 5.2 to 8.6 px: a code of digits is the widest) and gets a minimum width of the widest code in em, so it is right at any size: **`min-w-[4.53em]`** for `#rrggbb` (63.33 px at 14 px) and **`min-w-[5.83em]`** for `#rrggbbaa` (81.49 px), measured with the real font through the layout of a column of spans rather than guessed in `ch`. The text stays at the start, so a code of narrow letters leaves room at the end of the button. **Recipe:** `ColorInputStyle` gains `Code` (`tabular-nums min-w-[4.53em]`) and `CodeAlpha` (`min-w-[5.83em]`, added to `Code` while the input has `Alpha`); `Trigger` loses `tabular-nums`, which moved to `Code`. Part names are public API, so the choice was between these two fields and no recipe control of the width (the trigger's `Class` could only set the width of the whole button, not that of a code whose format changes with `Alpha`); another font needs its own widths, which is why they are recipe data. **Tests:** `TestColorInputCodeFollowsTheDrag` (mid-drag, no builds, the code on each move; the name after the drag) and `TestColorInputTriggerWidthIsStable` (the same width for eight colors, with and without `Alpha`). The goldens of the `ColorInput` sheet and of its open window change (the trigger is wider); the `ColorPicker`'s and every other component's are bit-identical. **Patch v0.10.3 (review fixes).** *Same frame for a controlled color:* a drag move of a controlled picker builds inside a frame (a click or a key builds before it, in the discrete flush, where `PublishValue` was already the direct store), and there `sync` → `repaint` and `UseColorField` published the field's text and the version that the button's code reads with `PublishValue`, whose build, text and field readers waited for the next frame: the hex field and the code showed the old color for one frame per move (measured: 2 frames per move, 1 for an uncontrolled picker). **Rule** (amends ADR-096's `PublishValue`): `core.PublishValue` called from a component build, in a frame or not, is the UI thread's direct store; every phase still to come in the frame (the rest of the build phase, styles, layout, texts, bound fields, paint) reads the value. A build is always before those phases, so nothing is lost; a build reader marked by it builds again in the same build phase. Place functions and `UseSize` publish outside builds and keep ADR-164's rule. Measured: a controlled picker and a controlled `ColorInput` 1 frame per move, the field and the code current in it. A swatch click and an arrow key in the field were already current in their frame, and a refused commit never flashed (the event and its build run before the frame). *Live code in the field:* `shownText` formats the color shown now (`shown`), like `follow`, instead of the color of the last build; in a build the two are equal (`sync` sets `built` to `shown` before the field's hook reads it, so a build during a drag never brought back an old code), but an event between builds (a paste put back while a second pointer drags) would have. *Name at rest:* there is no phase-deferred accessible name (no `AriaLabelFn`), and a name that changed per move would make assistive technology announce every move, so the button's `aria-label` keeps the color of the last build, as the thumbs' `aria-valuetext`: current at once when an uncontrolled drag ends (its end builds) or rests, and after every build of a controlled input (documented on `ColorInput.AriaLabel`). Tests: `TestColorControlledCodeInTheFrameOfTheChange`, `TestColorHexFieldBuildDuringADragKeepsTheCode`, `TestColorInputTriggerNameAfterTheDrag`. No golden changes.

## Rationale

A text that is a function of a value is the pattern the project already has for what changes every frame (`TextFn`), so the fix reuses it and keeps the rule of ADR-143 that a drag does not build; the width is the owner's choice (a fixed width, no `font-mono`): measuring the widest code is exact where `ch` (the width of the `0` of the font, not of its digits plus `#`) would have been a guess
