# ADR-129: `kit` design

- **Date:** 2026-10-25
- **Status:** Accepted

## Decision

`kit` design (phase 10; decisions K1–K17 are the owner's; amends §5's `kit` box, whose `tela add` stays deferred, and the phase-10 done criterion). **Shape (K1, K5).** Every component is a struct component (ADR-088) with its props as fields: `kit.Button{Variant: kit.Outline, Size: kit.Sm, OnClick: save, Children: h.Text("Save")}`. Each has `Class string`, appended after its recipe's classes on the root element (Tela's class order is last-wins, so overriding needs no tailwind-merge), and `Props tela.Child`, extra `h` props for the root element; common props have fields (`Disabled`, `OnClick`, `Type`, `AriaLabel`). Children are a `Children tela.Component` field; components with several parts take slots (`kit.Card{Title, Description, Action, Children, Footer}`, `kit.Dialog{Trigger, Title, Description, Children, Footer}`) and items as slices (`kit.Tabs[K]{Tabs: []kit.Tab[K]{…}}`), with `Render func(K) tela.Node` where items need custom rendering. **Values (K2, K4).** `type Variant string` and `type Size string` with shared constants (`Default` = "", `Secondary`, `Outline`, `Ghost`, `Destructive`, `Link`; `Sm`, `Lg`, `Icon`, `IconSm`, `IconLg`); a value the active recipe does not define panics in dev mode with the closest one and falls back to the default otherwise. State follows ADR-101: `Checked *bool`/`DefaultChecked`/`OnCheckedChange`, `Open *bool`/`DefaultOpen`/`OnOpenChange`, `Value *K`/`DefaultValue`/`OnValueChange`, `aria.Selection[K]` for several values. **Look (K3).** shadcn/ui v4, style `new-york-v4`, at one pinned registry commit, its class strings ported verbatim where Tela supports them (`data-[state=…]:` becomes `checked:` or an `aria-*:` variant, `[&_svg]:…` classes on the icon slots, `has-[>svg]:` a Go condition); `kit.Theme()` is shadcn's neutral theme with a 10 px radius. Conformance: a Chromium gallery of every component's static states, from shadcn's own markup with Tailwind 4.3.3 and shadcn's CSS variables, light and dark, scales 1 and 2, written with public API only (like `icons/lucide`'s), plus goldens. **Customization (K17), three levels:** theme tokens (ADR-089); recipes, the whole look of a component as data (a Go struct of class strings per part, variant, size and state): `kit.DefaultStyle()` returns a copy of the default recipes, the app edits it (`s.Card.Root += " backdrop-blur-xl"`, `s.Button.Variants["glass"] = "…"`) and `kit.StyleProvider{Style: &s, Children: …}` applies it to a subtree, where a variant is valid when the active recipe defines it; and per-instance `Class` and slot classes. Part names are public API; the Chromium check covers the default recipes only. **Toast (K6):** `kit.Toaster{Children: …}` and `kit.UseToast()`, a comparable handle safe from any goroutine; no global. **Icons (K7):** each file declares the Lucide icons it draws as unexported `tela.Icon` literals (ISC, `THIRD_PARTY.md`), and every icon slot is a replaceable `tela.Icon` field. **Behavior (K8)** stays in `aria`: new React Aria ports `UseRadioGroup`/`UseRadio`, `UseToggleGroup`, `UseSlider`, `UseProgressBar`/`UseMeter`, `UseMenuBar`, `UseContextMenuTrigger`, `UseCalendar`/`UseRangeCalendar`, `UseColorArea`/`UseColorSlider`; the engine gains `h.AriaInvalid` with `aria-invalid:` and `h.AriaSort`, and `i18n` the first day of the week from CLDR weekData. **Scope (K9, K10):** the roadmap's list plus ToggleGroup, AlertDialog, DropdownMenu, Label, Textarea, Separator, Skeleton and Field; the date picker is a button, a popover and a calendar (single date and range, limits, i18n names and first weekday; no time or typed segments); the color picker an SV area, a hue and an optional alpha slider, a hex field and optional swatches; the table sorts by header (`aria-sort`) with a sticky header and leading columns (no virtualization, resizing or editing); menus have no submenus. **Files:** one self-contained file per component importing only `tela`, `h`, `aria`, `i18n` and the standard library (shared types and the recipe struct in a base file), so a later copied-source distribution stays cheap. **Previews (K11):** goldens in `kit`'s tests, one sheet per component in both schemes and scales; an `examples/kit` gallery has one `Previews` entry per component; package `kit` declares no `Previews` (it would link every component into every app). **Examples (K12):** the app screens move to `kit`: dashboard (a glass style), settings (the default style), signup, pricing, board, player, i18n and native (Win11, Adwaita and Breeze as three styles); hello, counter, shapes, text, layout, motion, virtuallist and aria stay as they are, with bit-identical goldens; API gaps found while migrating go to the owner. **Done when** dashboard and native are built only on `kit`, settings uses the default style, no migrated example has a hand-made control or hand-drawn icon, and the other examples' goldens are unchanged

## Rationale

The owner's decisions. Structs give every prop a documented field and fit the struct components of ADR-088; slots are shorter than compound parts in Go and keep state inside the widget. Recipes make "customize everything" a data edit rather than a copy of the source, typed and scoped to a subtree like `h.Scheme`, and the dashboard's glass look is the test that they are enough; migrating the app screens is the test of the API before it freezes, while the examples that show a lower layer keep showing it
