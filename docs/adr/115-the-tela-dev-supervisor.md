# ADR-115: The `tela dev` supervisor

- **Date:** 2026-10-22
- **Status:** Accepted

## Decision

The `tela dev` supervisor (phase 9, T4; implements ADR-111 on ADR-112; amends §17's `tela dev` row with `-v`). **Command.** `tela dev [--size WxH] [--scale N] [--dark] [--preview NAME] [--no-state] [-v] [pkg]`, pkg defaulting to `.`. A package main is built as is; any other package, or any package with `--preview`, gets a generated runner like `tela snapshot`'s (same contract detection on the non-test files; the window comes from a package-level `App`, else 960×640): a non-main package gets a main package in `<pkg>/zz_tela_dev_main/` that imports it, and a package main gets `<pkg>/zz_tela_dev_preview.go`, whose `init` runs the preview with `tela.Main` and exits before the package's `main` (a package main cannot be imported); both exist only in a `go build -overlay`, so nothing is written into the package. An unknown preview name is reported by the runner (exit 1) before `tela.Main`. **Build.** `go build -tags teladev -o <tmp>/app-<n>[.exe] [-overlay ...] ./<pkg>` with `CGO_ENABLED=0`, run in the module root; the flags live in `devBuildFlags` (tuned for speed by ADR-116). The first build starts at once; a newer change cancels a running build (SIGINT to the go command, which stops its compilers; killed after 2 s; killed at once on Windows). After each successful build `go list -e -deps -json` refreshes what is watched. **Watcher** (`cmd/tela/internal/watch`, only `golang.org/x/sys`): inotify on Linux (a watch per directory, non-blocking descriptor in an `os.File` so `Close` unblocks the read as fsnotify does; new and moved-in directories are watched and scanned, moved-away subtrees unwatched, `IN_Q_OVERFLOW` reported as an overflow and the trees walked again, `ENOSPC` reported once with the sysctl fix); `ReadDirectoryChangesW` with the subtree flag and overlapped I/O on Windows (overflow = zero bytes or `ERROR_NOTIFY_ENUM_DIR`; skipped directories filtered by path; written to compile, not yet run on Windows); polling every 300 ms elsewhere (macOS until its phase). The filter runs before a trailing 100 ms debounce (at most 1 s from the first change), so irrelevant writes never delay a batch. Rebuilds on non-test `.go` and `.s` files (not under `testdata`, unless the app's own package is there), `go.mod`, `go.sum`, `go.work`, the `EmbedFiles` of the packages of the main module, of `go.work` modules and of local `replace` directories (all watched), and anything under the asset directories the child reports; skips hidden directories, `node_modules`, nested modules, the build directory, and editor temporaries (`*~`, `.#*`, `#*#`, `*.swp`/`.swo`/`.swx`, `4913`, `*.tmp`, `*.crswap`, GoLand's `___jb_tmp___`/`___jb_old___`); create-and-rename saves (vim, GoLand) and in-place writes (VS Code) are tested. **Supervisor.** One goroutine decides everything from an unbounded event queue (the host's callbacks only push events, so the host's UI thread never blocks; UI-thread work goes through `Host.Post`); the real window is the `auto` backend's (`TELA_BACKEND` honored) with a `remote.Host` on the main OS thread. Children run with `TELA_REMOTE`, `TELA_REMOTE_TAG` (the build generation), `TELA_DEVLOOP=1`, `TELA_DEVLOOP_NO_STATE=1` with `--no-state`, and `TELA_DEV=1` unless the user sets `TELA_DEV`; their stdout/stderr are forwarded, stdin is the null device, and they run in their own process group (Unix `Setpgid`, Windows `CREATE_NEW_PROCESS_GROUP`) so Ctrl+C reaches only tela dev, which stops them. **Swap.** After a good build, if a child is alive: `Freeze`; `state.save` to the active child (1 s; an error or no handler proceeds without state and says why); start the new child, answering its `state.load` with the bytes (empty for none); wait for its first frame (15 s); `Promote`; stop the old one (`tela.dev.quit`, then after 1 s close the connection and kill). A new child that exits, panics or times out before its first frame is killed, input is unfrozen and the old child stays. With no child alive (a runtime crash) the next good build starts fresh: no state, no freeze. Builds that finish during a swap wait for it; only the latest is swapped in. An exit is classified once the child's connection has ended (or 500 ms after the exit if it never connected), because its last control messages (a panic report) reach the supervisor through the host's UI thread, unordered with the process's exit. The active child exiting with status 0 (its window closed) quits tela dev, and so does a close request while no child is alive, `q`, SIGINT/SIGTERM/SIGHUP (a second one kills the children at once) and the end of the backend's loop (status 1). **Control kinds** (`internal/devloop`, standard library only, imported by `cmd/tela` and by `teladev` files): `tela.dev.state.save` (host→child request, reply opaque bytes), `tela.dev.state.load` (child→host request before mounting, reply the bytes or empty), `tela.dev.state.report` (child→host notification, two uvarints kept/reset, printed as "state: 12 kept, 1 reset"), `tela.dev.panic` (child→host notification, "panic: <value>\n\n<stack>", sent before a non-zero exit; the terminal gets one summary line since the child prints the trace on stderr), `tela.dev.assets` (child→host notification, NUL-separated absolute `os.DirFS` roots, the full list each time), `tela.dev.quit` (host→child notification: exit 0 promptly). **Flags.** `--size` rewrites the options of the real window (`HostOptions.WindowOptions`, new in `remote`), `--dark` forces `DarkMode` in the settings children see (`HostOptions.Settings`, new; a system change it hides is not forwarded) so `App.ColorScheme` still wins, `--scale` is `HostOptions.Scale`, `-v` prints each step and the timing of each reload. **Terminal** (`cmd/tela/internal/term`): when stdin is a terminal, cbreak mode (termios without `ICANON`/`ECHO`, keeping `ISIG` and output processing, so Ctrl+C still signals and children's `\n` still returns the carriage; console mode without line input and echo on Windows); `r` reload, `R` reload with fresh state, `q` quit; restored on every exit path, including panics on the supervisor's goroutines (each restores it before re-panicking). One line per event: `building…`, `started in …`, `reloaded in 280ms (state: 1 kept, 0 reset)`, `restarted in …` after a crash, `build failed:` and the compiler output, `the app panicked: …`. **Errors.** Problems go through one seam, `problemView{show(problem), clear()}` (kinds build, panic, exit, start; a one-line summary and the full text), printed by the terminal view; T5 adds the overlay over the last good frame there (`Host.SetOverlay`). **Measured** (Core Ultra 5 125H): with fake children (the test binary speaking the protocol) a reload takes 15 ms from the key to the promotion; with a real `go build` of the 84-line `cmd/tela/testdata/devfake` (warm cache, headless) a save reloads in 276–328 ms: 100 ms debounce, 172–224 ms build, 0.15 ms state save, 2.7 ms start to first frame, 0.05 ms promotion; on Wayland at `--scale 2` the first frame took 20 ms from the start and its promotion 5 ms. The end-to-end test on a real Tela app came with the child runtime (ADR-114)

## Rationale

One event loop with no locks around its state makes the swap's many asynchronous steps (build, save, process start, connection, first frame, exit) easy to reason about and to test with fake children; the host stays responsive because nothing waits on its thread. Process groups keep a terminal Ctrl+C from killing a child mid-swap. Filtering before the debounce, and watching only modules built from source, keep app logs and the module cache from triggering builds. The `init` runner is the only way to run a preview of a package main without copying it; the overlay keeps the source tree clean
