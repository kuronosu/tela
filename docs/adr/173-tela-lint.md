# ADR-173: `tela lint`

- **Date:** 2026-10-26
- **Status:** Accepted

## Decision

`tela lint [-json] [-tests] [packages]` (default `./...`) checks Go source statically, so the mistakes that dev mode reports at run time fail in CI with dev mode off (phase 11; amends §5 and §17). **Engine:** `internal/lint`, used only by `cmd/tela` (like `internal/icongen`); packages are found with `go list` and type-checked with the standard library (`go/parser`, `go/types`), no new dependency; the imports are type-checked from source, without function bodies, by a loader of its own that all packages of a run share (`go/importer`'s `source` importer would run `go list` once per import); a package that fails to type-check is reported and skipped. A value is checked when it is a **constant** string (a literal, a `const`, a concatenation of constants); anything computed is skipped, never guessed. **Rules**, each with the runtime's own check and message (the same "did you mean" as dev mode, from `internal/style` and `internal/semantics`): `class`: every string that reaches the class parser (`h.Class`, `h.Exit`, kit `Class`/`…Class` fields, kit recipe fields, `App` class fields and `ClassAliases` values), with the aliases (map literals given as `ClassAliases`) and theme color names (constant keys of `map[string]tela.SchemeColor` literals and assignments) declared in the linted packages known; `role`: `h.Role`; `aria`: the tokens of `h.AriaSort`, `h.AriaCurrent`, `h.AriaHasPopup`, `h.AriaOrientation` and `h.AriaAutoComplete`; `prop`: the other literal-validated arguments, `h.Dir`, `h.Type` (and the `Type` of `kit.Button` and `kit.Input`) and `tela.Ease`, each through a pure check factored out of the prop (`internal/core/validate.go`); `key`: a constant `h.Key` repeated among the children of one element, and the list without keys that dev mode warns about; `hooks`: React's rules of hooks as dev mode applies them (ADR-085, ADR-088): a hook (`Use…` of `tela`, `aria`, `kit`, `i18n` or a custom hook) called conditionally, in a loop, after an early return, from a function that is neither a component nor a custom hook, or in a function literal that is not a component; and a component that uses hooks called directly instead of through `tela.C`, `tela.CP` or an element (a function `func() tela.Node` or `func(P) tela.Node` is given the benefit of the doubt, and a custom hook is a function named `UseXxx` or `useXxx` that calls a hook). **Output:** `file:line:col: rule: message`, sorted, like `go vet`; `-json` for tools (and `tela mcp` later); exit status 1 when anything is reported and 2 on a usage error or a package that cannot be loaded; `severity` is `error`, or `warning` for the `key` findings, which dev mode only warns about. `_test.go` files are skipped unless `-tests` is given (tests often use a wrong value on purpose). **Suppression:** a `//tela:ignore <rule>` comment on the line or the line above. The repository lints clean, and CI runs `tela lint ./...`.

## Rationale

Typos in classes are the commonest mistake an agent makes in Tela, and dev mode only shows them on a screen that renders them. Reusing the runtime's checks keeps one source of truth for what is valid and for the suggestions. Constants only, so a report is never a guess; type information (not names) is what tells `h.Class` from another `Class`, sees through dot imports and reads `const` class strings, and the standard library provides it without `golang.org/x/tools`.
