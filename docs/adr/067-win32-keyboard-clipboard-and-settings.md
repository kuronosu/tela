# ADR-067: Win32 keyboard, clipboard and settings

- **Date:** 2026-10-13
- **Status:** Accepted

## Decision

Win32 keyboard, clipboard and settings (phase 5; completes ADR-063; implements ADR-050 on Windows). A press is built from its messages: `WM_KEYDOWN` gives the physical key (scan code with the extended flag, through the W3C table) and the virtual key; the `WM_CHAR`s that `TranslateMessage` posts before dispatching it give the text, found with `PeekMessageW(PM_NOREMOVE)` over the character range only (a wider range finds a queued key release first, and the `PM_QS_*` flags miss characters a previous peek has seen); a press followed by characters waits for them, any other is delivered at once. `Key` asks the layout with `ToUnicodeEx` on a copy of the keyboard state without Ctrl and Alt (AltGr kept) and `wFlags` 4, which leaves the kernel's dead-key state alone (the call is repeated for a dead key where the flag is ignored); a composed press has the composed character as `Key` and `Text`, and a dead key followed by a key that does not compose types both (`"´x"`, `Key` "x", as winit). With Ctrl held `Text` is the layout's character, not the control code; control characters are never text (Enter after a dead key keeps the accent Windows types first as its `Text`); a dead key's release is `Dead` too. AltGr is found per layout (Ctrl+Alt changes a character in `ToUnicodeEx`) and arrives as a left Ctrl and a right Alt with the same message time: the Ctrl, recognized by peeking at the next message, produces no event, the Alt is `AltGraph`, and `Mods` reports neither while the right Alt is held (a left Ctrl whose press was delivered stays Ctrl; Ctrl+Alt on the left is Ctrl and Alt, as on Linux, though Windows types AltGr characters for it). Modifier repeats are dropped; Windows repeats only the last key pressed, so holding "a" and pressing Shift stops the repeat. A window without focus reports no keys; system keys are swallowed so that a lone Alt or F10 does not enter a menu loop (`SC_KEYMENU` is dropped), except Alt+F4 and Alt+Space, which go to `DefWindowProc` and are not reported; held keys whose release a modal loop ate are released synthetically at `WM_EXITMENULOOP`/`WM_EXITSIZEMOVE`. `VK_PACKET` text (`SendInput` Unicode) is a press with an unidentified code. Clipboard: `CF_UNICODETEXT` with the message-only window as owner and a 100 ms retry of `OpenClipboard`; `ReadText` posts the read to the loop and returns LF text (CR LF and lone CR become LF), `WriteText` stores CR LF (browsers on Windows do the same) and drops NUL. Settings: dark mode is `AppsUseLightTheme` = 0 (light if absent), reduced motion is `SPI_GETCLIENTAREAANIMATION` off; `WM_SETTINGCHANGE`, broadcast to top-level windows only, re-reads all values and queues one `SettingsEvent` when any changed; title bars follow dark mode with `DWMWA_USE_IMMERSIVE_DARK_MODE` (20, then 19)

## Rationale

winit's Windows keyboard is the reference that survived years of layouts; the sequence of messages is the only place the dead-key result exists, and `ToUnicodeEx` with the keep-state flag is the only way to ask the layout without disturbing it; AltGr as "Ctrl and Alt" would fire shortcuts when typing "@" on German keyboards; browsers use CR LF on Windows and LF everywhere else
