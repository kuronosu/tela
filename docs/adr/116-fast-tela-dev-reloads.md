# ADR-116: Fast `tela dev` reloads

- **Date:** 2026-10-22
- **Status:** Accepted

## Decision

Fast `tela dev` reloads (phase 9, T6; implements G7 of ADR-111 on ADR-115). **Method.** `tela dev -v --size 1920x1080 ./examples/dashboard` in the repository (a git checkout), headless backend (`TELA_BACKEND=headless`, scale 1), warm build cache, three edits of `Sidebar` in `chrome.go` repeated five times, each with new content so no compile is a cache hit: a class (`p-5` to `p-[20.Npx]`), markup (a new `Div` with a `Text`) and a new hook (`tela.UseState(N)`, which resets `Sidebar`); timings from the `-v` line (save → build start is the 100 ms debounce, then build, state save, start → first frame, promotion), medians of 5 in ms, on a Core Ultra 5 125H, with the go command and the children capped at 4 CPUs (a systemd scope with `CPUQuota=400%`) unless "no cap" says otherwise; the child's own steps were timed with temporary trace points (not committed). **Before** (3e12511, `-tags teladev` only): class 100 / 626 / 0.7 / 119 / 0.8 = 845; markup 100 / 638 / 0.7 / 121 / 1.0 = 862; hook 100 / 624 / 0.7 / 115 / 0.8 = 845; all fifteen 855 (830–895); no cap 817 (804–839). **After:** class 100 / 417 / 0.8 / 107 / 0.9 = 629; markup 100 / 417 / 0.7 / 102 / 1.1 = 622; hook 100 / 405 / 0.9 / 102 / 1.0 = 611; all fifteen 621 (607–634); no cap 588 (580–658). Live on Wayland (Hyprland, the window on a virtual 1920×1080 output at scale 2, so 1920×1080 device pixels; no cap): class 604, markup 612, hook 605, all 608 (587–629), build 405–412, start → first frame 90–93; the frame reaches the screen at the window's next frame callback after the promotion. `TestDevEndToEnd` (ADR-114) went from 0.67–0.71 s to 0.50–0.52 s per reload. G7's 1.5 s target and its 1 s stretch are both met. **Build flags** (`devBuildFlags`, `cmd/tela/dev_build.go`; a copy of the dashboard in a module outside git, one unique edit per build, medians of 7 builds, capped): `-tags teladev` alone 618; `-ldflags=-s -w` 501 (`-w` alone 512): no symbol table and no DWARF, the link writes less; panics keep `file:line` because the runtime reads pclntab, and `runtime.FuncForPC` (component names, ADR-113's identity) keeps its names (`TestDevBuildKeepsFileLines`); a debugger cannot attach to a dev build. Adding `-gcflags=-l` 412: inlining is most of what the compiler spends on the app's package (872 functions with inlining, 790 without; front end 91 → 55 ms); a `-gcflags` without a pattern applies only to the package named, the app's main package or the generated runner, so Tela and the other dependencies keep their flags and their cached builds and only the app's own code runs without inlining in dev (release builds are untouched, and identity by function name no longer depends on inlining decisions). `-gcflags=-N -l` 420: no further gain, so the compiler's optimizations stay. `-buildvcs=false` saves about 26 ms in a git checkout (the stamp runs git on every build; measured as link-only builds of the in-repository dashboard, 524 → 498), nothing outside one; dev mode stays on, since the supervisor sets `TELA_DEV=1` and a binary without the stamp and without `-trimpath` is no release build anyway (ADR-085). Not adopted: `-trimpath` (610, no gain, and it would make the binary a release build), building into one output path instead of a new one per build (618 vs 609, noise; new paths stay, since the old child still runs its binary), `GOGC=200`/`400`/`off` for the go command (496–502 vs 502; the compiler already sizes its own heap). A `-buildvcs`, `-ldflags` or `-gcflags` in `GOFLAGS` (read once with `go env GOFLAGS`, so `go env -w` counts) is left to the user, because the command line would replace it. Where a build goes now: about 45 ms of go command (package loading and the cache checks of ~400 actions), 160–190 ms compiling the dashboard's package (parse and type check 44, SSA 76 at the default `-c=4`, object file 26) and 155–185 ms linking a 21 MB binary (loading the objects 50, dead code 36, pclntab 28; the embedded fonts are 8 MB of it). **Child start-up:** 3 ms to `core.Run`, then the embedded fonts: 72 ms parsed one after another, of which Noto Color Emoji is 37–51 ms (go-text parses every glyf outline of the font up front); `text.embeddedTypefaces` now parses the six files concurrently and assembles them in the same order, 52–57 ms (benefits every app's start, not only dev children); the system font index is lazy and not on this path; then 0.5 ms to dial the supervisor and load the state, 2 ms to mount, 38 ms for the first frame at 1920×1080 (build, layout, raster with the backdrop blur), 3 ms until the supervisor sees it; the state save and the promotion stay under 2 ms. Not adopted: starting `go list -deps` (the watch refresh, 56 ms of CPU) after the promotion instead of beside the swap (−1 ms, noise). The debounce stays 100 ms (the owner's decision, not the bottleneck). **What would go further:** starting a build at the first change and restarting it on a later one would take the 100 ms debounce off the critical path (a change of G6a, the owner's call); parsing the emoji and Arabic faces lazily, when fallback first needs them, would take about 40 ms off every start (a change in `text`'s candidate lists); the go command, the compile of one package and the link are otherwise at what the toolchain allows

## Rationale

The build is two thirds of a reload and the toolchain's defaults favor release binaries; dev builds need neither debug sections nor inlined app code, while the dependencies, which are cached and do the rendering, keep their optimizations. Leaving flags set in `GOFLAGS` to the user keeps `tela dev` from silently overriding a project's `-X` or `-gcflags`. Parsing the embedded fonts concurrently gives the same typefaces with less wall time on every start, without changing how fallback works
