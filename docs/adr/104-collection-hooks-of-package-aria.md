# ADR-104: Collection hooks of package `aria`

- **Date:** 2026-10-21
- **Status:** Accepted

## Decision

Collection hooks of package `aria`: `UseListBox`, `UseMenu`, `UseTabs` and `aria.Selection` (phase 8, T8a; the shapes follow the owner's decisions on keyed collections and on the selection type, the names the owner has not seen are listed for review; amends §14, ADR-100 and ADR-101). **Keyed collections.** `UseListBox[K comparable](ListBoxOptions[K])`, `UseMenu[K](MenuOptions[K])` and `UseTabs[K](TabsOptions[K])` take `Keys []K` (the items in display order, given on every build), `DisabledKeys []K` and `TextValue func(K) string` (typeahead), and return a result that embeds `Collection[K]` (`ItemProps(k) tela.Prop`, `ItemRef(k)`, `IsSelected`, `IsDisabled`, `IsFocused`, `IsFocusVisible`, `Focused() (K, bool)`, `FocusKey`, `Focus(strategy)`, `ClearFocus`, `HandleKeyDown`, `ActiveDescendant`, `Section(name)`) next to `Props`, `Selected` and `Ref`; `TabsResult` adds `TabProps` and `PanelProps(k)`. A hook can not be called once per item, so the state is one `collState` per hook call (made with `UseOnce`, read and written directly by the handlers, so a second event before the next build sees the first, as `boolState` does; a counter in `UseState` asks for the build), and every key has an `ElementRef` made by the new `core.NewElementRef()` (a ref that belongs to no hook slot; the engine already detaches it when its element unmounts), which `ItemProps` attaches: that is how a key becomes a DOM focus, a scroll, a bounds query (page keys), `aria-activedescendant`, `aria-controls` and `aria-labelledby`. The refs of keys that leave `Keys` are dropped. An item element holds one ref (ADR-101): `ItemRef(k)` is the one to share. **`aria.Selection[K comparable]`** (the owner's decision; the exact shape is listed for review) is an immutable set, `struct{ s *selectionSet[K] }`: the zero value (`s == nil`) is "not given", which makes an option uncontrolled, and `SelectionOf[K](keys...)` is a value even when empty (a controlled, empty selection); `All[K]()` is React Aria's `"all"`. Methods never change the receiver: `Has`, `With`, `Without`, `Toggle`, `Len`, `Keys` (insertion order, a copy), `In(order)` (the keys in a collection's order: "iteration in key order"), `First()`, `Resolve(order)` (All to its keys), `IsAll`, `IsEmpty`, `IsSet`, `Equal` (by keys, whatever the order; an All and the set of all keys are not equal), `String`. It is comparable with `==` (identity: two equal sets are not `==`, `Equal` compares keys) and usable in `tela.UseState` and as a map key. `Len` and `Keys` of All are 0 and nil (it does not list keys) and `Without` on All returns it unchanged (resolve first). **Controlled or not** follows ADR-101: a non-zero `Selected` is controlled (the list shows it and `OnSelectionChange(Selection[K])` only asks; a selection the app does not store is refused), `DefaultSelected` starts an uncontrolled one, the callback is also called for an uncontrolled list, and an equal selection is not reported. Tabs take the same type (the selected tab is `Selected.First()`); no `SelectedKey *K` was added. Modes are strings, as in the other options of the package (`SelectionMode` `"none"`, `"single"`, `"multiple"`; `SelectionBehavior` `"toggle"`, `"replace"`; `Orientation`; `Direction` `"ltr"`, `"rtl"`; `KeyboardActivation` `"automatic"`, `"manual"`; `EscapeKeyBehavior`; `FocusStrategy`): an unknown one panics in dev mode with the closest valid one. **Rules (React Aria's `useSelectableCollection`, `useSelectableItem`, `ListKeyboardDelegate`, `useTypeSelect` and `SelectionManager`).** ArrowDown and ArrowUp (ArrowLeft and ArrowRight for `Orientation: "horizontal"`, swapped by `Direction: "rtl"`), Home, End, PageUp and PageDown (a viewport away: the item count is the container's height over the stride of the items that are rendered, so keys of a `h.VirtualList` that are not rendered count), `ShouldFocusWrap`, disabled keys skipped, typeahead (case-insensitive prefix, starting at the focused key and then from the top; the 1 s buffer is `core.UseTimeout` on the frame clock, no goroutine; a space inside a search is a character), Shift+arrows and Shift+click extend from the anchor, Ctrl (Cmd on a Mac) +A selects `All` (unless `DisallowSelectAll`), Ctrl+click and Ctrl+Space toggle, Ctrl+arrows move without selecting, with `SelectionBehavior: "replace"` moving the focus moves the selection, Escape clears the selection (`EscapeKeyBehavior`), touch and virtual presses toggle (they have no modifier keys). `OnAction` follows React Aria's primary and secondary actions: with `"toggle"` it runs when the selection is empty, with `"replace"` a click selects and a double click or Enter runs it. A press is a pointer down (it records the pointer type; with a virtual focus it sets the highlight) plus a click, so touch, pen, the semantics click and `ElementRef.Click` are all presses and selection happens on release, as React Aria's `onPress`; Enter and Space are handled by the collection's key handler on the focused key at the key down (not repeats), which stops them. Items are not Buttons (a Button's own Enter and Space click would act twice): use `Div` or `Li`. **Focus.** A roving focus by default: the focused item's element has the focus and `TabIndex(0)`, the others -1, a disabled one none, and the collection is a tab stop (`TabIndex(0)`) only while no key is focused; when it takes the focus (Tab, or a press on it or on a disabled item) the focus goes to the focused item, else to the first selected one, else to the first. Moving the focus focuses the element, which the engine scrolls into view; a key whose item is not rendered (`h.VirtualList`) becomes `pending`: the list scrolls to its index (`ElementRef.ScrollToIndex` through the `Ref` that `Props` carries, so `Props` go to the `VirtualList`) and `ItemProps` gives that item `h.AutoFocus(true)`, so it takes the focus when it mounts. If the focused key leaves `Keys` the focus moves to the item that takes its place (react-stately's `useListState`). `AutoFocus` and `FocusStrategy` (`FocusFirst`, `FocusLast`, from `UseMenuTrigger`; a strategy implies `AutoFocus`) focus on mount: the first selected item, else the strategy's, else the collection itself; it applies when the hook mounts, so the component that calls `UseMenu` is rendered only while the menu is open (a menu that stays mounted when closed does not focus again). **Virtual focus.** `ShouldUseVirtualFocus`: the collection is the tab stop and keeps the DOM focus, the items are not focusable, the focused key is highlighted (`IsFocused`) and `aria-activedescendant` points to its ref, scrolled into view with `ScrollIntoView` (or `ScrollToIndex`). `ExternalFocus` (an addition for T8b's combobox, listed for review) is that for a collection that never has the focus: no tab stop, no handlers on `Props`, a press on an item does not move the focus (its pointer down is prevented), and the element that has the focus calls `HandleKeyDown` from its key handler and carries `ActiveDescendant()`; the keys of a text field stay its own (it handles the arrows, PageUp, PageDown and Enter: no Home, End, Space, Ctrl+A, Escape or typeahead). **Menu.** `UseMenu` adds the `menu` role and items that are `menuitem`, `menuitemradio` (`SelectionMode: "single"`) or `menuitemcheckbox` (`"multiple"`) with `aria-checked`. It adds no focus scope: the `MenuProps` of `UseMenuTrigger` hold the one with `Restore` and the label from the trigger, and `Ref: mt.MenuRef` is shared. The mouse focuses the item it moves over; choosing an item (click, Enter, Space) selects it as the mode says, calls `OnAction(key)` and then `OnClose` (the trigger's `Close`) unless `CloseOnSelect` (a `*bool`; nil closes unless the selection is multiple) says not to. A single selection never unchecks by choosing the checked item (`DisallowEmptySelection`; React Aria's menu would). **Tabs.** `UseTabs` is `useTabList`, `useTab` and `useTabPanel` in one hook: `tablist` with `aria-orientation`; `tab` with `aria-selected` and, while selected, `aria-controls` the panel's ref; `tabpanel` named by its tab (`aria-labelledby`) with `TabIndex(0)`. Only the selected tab is a tab stop (the list has none); automatic activation selects on focus (`SelectionBehavior: "replace"`), `"manual"` selects with Enter and Space; the arrows wrap; there is always one selected, enabled tab (the first when none is given or the given one is disabled or gone; a controlled value that does not hold is shown fixed, without calling the app). **Sections.** `Section(name)` returns `{Props, HeadingProps}`: a `group` named by its heading (`presentation`); the keys stay one flat list. **Engine (small, tested).** (1) `core.NewElementRef()`. (2) `UseMenuTrigger` focuses its trigger at the press start of a mouse or a pen before it opens the menu (React Aria's `usePress` does): the menu's `Restore` scope remembers the focus when it mounts, which is before the engine focuses the pressed button, so after a mouse open, Escape or choosing an item gave the focus back to nothing. Every golden is bit-identical.

## Rationale

The owner's shapes (keyed collections, `Selection` as an immutable set with "all", controlled when non-nil, options in and results with `Props` out). One state per hook with a ref per key is the smallest design that keeps `ItemProps(k)` for any number of items: no hook per item and no new engine concept besides a free ref, and the same machinery serves a `VirtualList`. A pending key plus `AutoFocus` on the item that mounts reuses the focus work of the frame, where an effect would have to run after the builds of the list, which a component's effect does not see. Selection on release and the pointer type taken at the pointer down give React Aria's rules with one handler pair per item. The oracle for the printed roles and states is Playwright 1.61.1 in Chromium, with the checker of ADR-096 (not part of the repository): seven trees (a single and a multiple list box, sections, a menu with a disabled item, radio and checkbox menu items, a tab list with its panel) print byte for byte as Tela prints them (`listbox`, `option [selected]`, `option [disabled]`, `group`, `menu`, `menuitem`, `menuitemradio [checked]`, `menuitemcheckbox [checked]`, `tablist`, `tab [selected]`, `tabpanel`). Telatest covers keyboard navigation (Tab in, Home, End, wrap, disabled keys, typeahead and its expiry on the frame clock, PageUp and PageDown, in a `VirtualList` of 1,000 rows too, where typeahead and End focus rows that are not rendered), single and multiple selection, toggle and replace, Shift ranges with keys and with Shift+click, Ctrl+click, Ctrl+A with a disabled key, controlled (and refused) and uncontrolled, actions and the double click, touch toggling, roving and virtual focus, an external focus driven by an input, the removal of the focused key, auto focus, horizontal and right-to-left lists, sections, menus opened with ArrowDown (first), ArrowUp (last), Enter, Space and the mouse, an action that closes and restores the focus, Escape, hover focus, disabled items and typeahead in a menu, checkbox and radio items, `CloseOnSelect`, tabs with automatic and manual activation, orientation, direction, disabled tabs, the panel link and a controlled selection. Known gaps: no submenus, `DisabledBehavior: "selection"`, per-item `closeOnSelect`, press, drag and release across menu items, links, drag and drop or grid layouts; `h.VirtualList` is vertical, so a horizontal list can not be virtualized; Shift+Tab into a collection focuses the first item, not the last (the focus event has no related target); the container's scroll position is not restored on focus; `PanelProps` always sets a tab stop, even when the panel holds focusable content (add `TabIndex(-1)` after it); items have no `aria-posinset` or `aria-setsize`.
