# ADR-160: Focus containment beyond Tab

- **Date:** 2026-10-25
- **Status:** Accepted

## Decision

Focus containment beyond Tab (v0.10.1; engine only, no API change; amends ADR-056, ADR-096 and ADR-101, and closes the gap ADR-137 records for `kit.AlertDialog`). `core.Scope{Contain}` constrained only Tab and Shift+Tab, so a press on the scrim of an alert dialog (it hits the window root, outside the modal) blurred the focused button and the focus went nowhere until the next Tab. **Rule** (React Aria's `useFocusContainment` in `FocusScope`, with the browser outcome of Radix's `AlertDialog`, whose prevented pointerdown outside leaves the focus where it is): while a containing scope is active (the existing `activeScope`: the most recently mounted containing scope that is not inert nor outside the active modal; nested scopes need no scope tree, since only that one holds the focus), inside it means its subtree in the element tree, so the content of Portals and overlays opened from inside it (a Select's list, a Popover, a nested dialog) is inside and is never fought over. (1) A primary press on nothing focusable (`mouseFocus` finds no focusable element at or above the target), outside or inside the scope, leaves the focus where it is when it is inside the scope, exactly as a prevented pointerdown does: no `OnBlur`, no change of the sequential navigation starting point, and `focus-visible` keeps what the heuristic gives a prevented press (`noteMouse` runs, `lastType` is not set to mouse), which is Chromium's behavior when a pointerdown's focus change is prevented: the element keeps its state (a ring shown by Tab stays, a press-focused element stays without one). (2) A focus change to an element outside the scope, by a press on a focusable element that is still hit (an overlay alive above a modal, such as a notification, or any element around a containing scope that is not modal), a Label's forwarded focus, or a script (`ElementRef.Focus`, telatest's `Focus`, the focus manager, `AutoFocus`, the restoration of another scope), does not happen (`trapping`, `keepInScope` in `focus.go`): the focus stays where it is when it is inside the scope, otherwise it goes to the element focused last inside it (`focusScope.last`, recorded by `setFocus`) while that is focusable, else to the scope's first tabbable element, else its first focusable one. The press itself is still delivered (its click runs), as in the browser. (3) `ElementRef.Blur` on an element inside the active containing scope does nothing (React Aria's blur listener focuses it again). Not leaving: the window losing the focus (the element stays focused, ADR-100); the fix-up blur of a focused element that stops being focusable and its unmount still leave nothing focused (the next Tab or focus change brings the focus back inside); a scope without `Contain` and non-modal popovers keep today's behavior (a press outside dismisses or blurs). **Deviation from React Aria:** it lets the focus reach the outside element and moves it back in its `focusin` (or, for a blur to the body, a `requestAnimationFrame`) listener, so handlers see the focus go out and come back; Tela checks before the change, so a re-trap is at most one focus change, to an element inside, made by the code path that asked (no event storm, no re-entrant flush: the change goes through `setFocus` and `afterFocusEvent` like any other). A combobox inside an alert dialog whose list is not dismissed by outside presses keeps its list open on a scrim press (the focus does not leave the input), as in the browser with Radix. **Tests:** `internal/core/focus_contain_test.go` (presses on nothing focusable inside and outside, presses and scripts aiming outside, the focus manager, Blur, a Portal inside the scope, focus-visible kept on and kept off, window focus, the fix-up and the last-focused fallback, nested scopes, a scope that stops containing; each step asserts the exact focus and blur events), `TestFocusScope` (a script cannot move the focus out of a containing scope), `kit/focus_contain_test.go` (an alert dialog's scrim press keeps the focus with no events and the Tab order goes on from it; a Dialog's scrim press still closes it and restores the focus; a Select and a Popover inside an alert dialog take and give back the focus, Escape and a scrim press close only them; an overlay mounted above the alert dialog stays clickable but neither its press nor a programmatic focus takes the focus), and `TestAlertDialogNeedsAnAnswer` now expects the focus on Cancel after the scrim press.

## Rationale

Containment is the promise of a modal: a press on the scrim must not leave the keyboard user with nothing focused, and an alert dialog is exactly the case where the browser (Radix) keeps it. Checking before the change gives the outcome of React Aria's re-focus without the out-and-back events that Tela's synchronous focus handlers would otherwise see, and reusing the active scope that already decides Tab keeps one notion of which scope holds the focus
